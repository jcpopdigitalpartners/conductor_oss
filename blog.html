Orchestrating a D&D Quest with Conductor OSS

Workflow orchestration, fork/join scouting, and a human-in-the-loop dungeon master

Most workflow-engine tutorials start with order fulfillment: charge the card, ship the box, send the email. That’s fine, but it doesn’t show why orchestration is fun to think about.

I wanted a demo where branching, parallelism, randomness, and “wait for a human” feel natural — so I built a Dungeons & Dragons quest pipeline in Conductor OSS.

The code is JSON. No custom workers. No microservices. Just a workflow definition, a local server, and a CLI. Somewhere between the tavern briefing and the boss fight, Conductor stopped and asked me to make a decision like a dungeon master.

That’s when it clicked.

TL;DR

  • Three workflow demos in conductor_oss: hello-world, hiring pipeline, D&D quest.
  • The quest uses SWITCH, FORK_JOIN, HUMAN, and TERMINATE — no custom backend.
  • Run locally with conductor server start + Java 21.
  • The hard parts were operational: WSL + SQLite on /mnt/c/, stale IDs, UI search — not the JSON.

Why Conductor?

Conductor is a workflow orchestration engine originally from Netflix. You define processes as JSON. A server executes them durably — if a step fails or the process pauses for days, state is preserved.

The pipeline

Validate → Party sheet → Tavern → d20 travel ├─ ambush (+ possible TPK) ├─ merchant └─ quiet road → Enter dungeon → FORK (stealth / arcana / religion) → JOIN → Intel report → HUMAN: DM crossroads → stealth | assault | parley → Boss fight → loot or retreat

The pause is the point. The workflow stops at dm_crossroads_ref until a human completes the HUMAN task — it waits, durably, until you send the next signal.

Running it (WSL)

  1. Start the server

    cd ~
conductor server start
    Start from ~, not /mnt/c/.... SQLite shared memory fails on Windows mounts.

  2. Register the workflow

    conductor workflow create dnd_quest_pipeline.json

  3. Start a quest

    conductor workflow start -w dnd_quest_pipeline -f sample_quest_input.json

  4. Play the DM

    conductor task update-execution \
  --workflow-id <workflow-id> \
  --task-ref-name dm_crossroads_ref \
  --status COMPLETED \
  --output '{"approach":"stealth","dmNotes":"Shadows favored."}'

What broke

SQLite on /mnt/c/

SQLITE_IOERR_SHMOPEN — disk I/O error (shared memory)

Fix: start the server from ~.

Workflow not found

Register before you run: workflow create then workflow start.

Executions hidden in UI

Executions tab → search by name → click Search. Not Definitions.

What I learned

  1. Orchestration shines when the process is messy — randomness, parallelism, early exits, human choice.
  2. HUMAN tasks are the “aha” — that’s not a queue; that’s orchestration.
  3. INLINE tasks are enough for demos — production swaps them for workers; the graph stays the same.
  4. Operations > definitions — WSL and SQLite cost more time than the JSON.
  5. GitHub Pages ≠ deployment — great for JSON; still need a Java server to run.

Taking it to the next level

The demo is intentionally self-contained: GraalJS INLINE tasks simulate dice rolls, workers, and narration. The workflow graph is the real artifact. Here’s how you’d evolve it without changing the story.

Notify the DM when the crossroads arrives

Instead of polling the UI, fire an event handler when a HUMAN task starts — ping Slack, email, or start a notification sub-workflow. The quest stays paused until the DM completes the task.

Swap INLINE for a real worker

@worker_task(task_definition_name="boss_encounter")
def resolve_boss(combat_state: dict) -> dict:
    return run_combat_rounds(combat_state)

Same workflow graph. Task type changes from INLINE to SIMPLE.

Deploy beyond localhost

Docker on a VPS, Railway, or Fly.io — or managed Orkes Conductor. Keep workflow JSON in git; CI registers definitions on merge. GitHub Pages hosts the story; the engine still needs a JVM somewhere.

Define the story as data. Run the boring parts. Pause where humans belong.

That’s worth a d20 roll.
